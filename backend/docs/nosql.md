# Oracle NoSQL Database

## Concepts

Oracle NoSQL Database is schema-full: a table must be created explicitly
(DDL) before you can put rows into it — there is no implicit
create-on-write.

| Oracle NoSQL         | Rough RDBMS equivalent          |
| --------------------- | -------------------------------- |
| Store (KVStore)       | Server instance / cluster        |
| Namespace (optional)  | Database + schema, combined      |
| Table                 | Table                            |

- Namespaces are optional; unqualified tables live in a default namespace.
  They exist for grouping tables and per-namespace grants in multi-tenant
  setups — not needed for a single small app.
- DDL (via `TableRequest`, or the SQL shell): `CREATE TABLE`, `DROP TABLE`,
  `ALTER TABLE` (schema evolution), `CREATE INDEX`, `DROP INDEX`.
- `SHOW DDL <table>` returns the table's `CREATE TABLE` statement (closest
  equivalent to MySQL's `SHOW CREATE TABLE`).
- Oracle Cloud Always Free tier: max 3 tables per tenancy (limit is
  tenancy-wide, not per namespace), 25GB storage/table, 133M reads + 133M
  writes per month.
- `ping` reports store-level health (shard/admin/replication-node status),
  not application data — useful to confirm the store itself is reachable
  and healthy before debugging anything else.
- The SQL shell prints `SELECT` results as one JSON object per row by
  default. Run `mode column;` for an aligned table view instead (also
  available: `LINE`, `JSON -pretty`, `CSV`).

## Design notes: "latest N per group" queries

Oracle NoSQL's SQL has no window functions (no `ROW_NUMBER() OVER
(PARTITION BY ...)`) and no `UNION`; `GROUP BY` only returns one aggregated
row per group. So there is no single-query way to get "the latest N rows
per group" (e.g. latest N posts per language).

The workable pattern:

- Model the group column as the shard key (or put a secondary index on
  `(group, sort_key)`), then run one range-scan query per group value and
  merge the results in application code:
  `SELECT * FROM posts WHERE language = ? ORDER BY id DESC LIMIT n`.
- Avoid using a plain timestamp (e.g. `created_at`) as the trailing key
  column — two rows can get the same timestamp and collide (a `PUT`
  silently overwrites the earlier row; an `INSERT` fails). Use a **UUIDv7**
  as `id` instead: it's unique (random bits) and, because the leading bits
  encode a millisecond timestamp, sorts lexicographically in creation
  order — so `ORDER BY id DESC LIMIT n` alone gives "latest N" without a
  separate `created_at` tiebreaker column.
- No built-in UUIDv7 generator (`random_uuid()` / `GENERATED BY DEFAULT`
  only produce UUIDv4); generate it in the application instead.

## Local setup (this project)

Local development uses the KVLite Community Edition Docker image
(`ghcr.io/oracle/nosql:latest-ce`), started via `backend/docker-compose.yml`:

- Container name: `emoji-generator-nosql`
- Hostname: `kvlite`; port `8080` (proxy, used by the app)
- Store name: `kvstore` (KVLite default, not overridden)
- Data persists in a named Docker volume; `docker compose down -v` wipes it.

The app connects via the `borneo` SDK (`app/database.py`), which exposes a
`NoSQLHandle` as a `wireup` injectable. The endpoint is controlled by the
`NOSQL_ENDPOINT` env var (default `http://localhost:8080`).

## Commands

```sh
# start
docker compose up -d --wait
# stop
docker compose down
# health check (store/shard/admin/replication-node status)
docker exec -it emoji-generator-nosql java -jar lib/kvstore.jar ping -host kvlite -port 5000
# interactive SQL shell (SELECT, CREATE TABLE, SHOW DDL, ...)
docker exec -it emoji-generator-nosql java -jar lib/sql.jar -helper-hosts kvlite:5000 -store kvstore
```
